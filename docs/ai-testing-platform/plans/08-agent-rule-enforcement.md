# 08 · Agent 规则强制（Enforcement）

**状态：设计** ｜ 适用范围：**平台级底座**（不限测试域）

> 问题：如何让 agent（开发中/使用中）**强制**遵守平台的规矩？不管用哪个 agent 都要遵守。
> 结论：**不强制 agent 的行为，强制行为的「效果」。**

---

## 1. 核心原则

**Agent 是随机的，你无法保证它"想"什么。** 任何试图"让 agent 遵守"的做法（写进 CLAUDE.md、prompt 叮嘱）本质是**建议**，agent 可忽略——**不是强制**。

**强制的本质**：agent 的所有动作，必须经过我们控制的关口才能生效。不合规的动作**不生效**——不是"告诉它别做"，而是"做了也没用"。

> **把强制从「agent 的行为」移到「行为的后果」。**

## 2. 为什么必须这样（而不是靠 hook）

强制机制**不能依赖**：

| ❌ 不能依赖 | 原因 |
|---|---|
| agent 的配合 | 它可能忽略指令 |
| agent 的 hook 系统 | 不是每个 agent 都有；且是 agent 侧，可被绕过 |
| agent 的特定 runtime | 换 agent 就失效 |

**必须依赖**：**所有效果都必经的关口**。

> **统一原理：平台定义规则，agent 只是"生产者"，它的产出必须过门才生效。**
> 因此无论哪个 agent，强制都是**同一套门**——门是强制的载体，天然与 agent 无关。

## 3. 四层防御（纵深）

```
Layer 4  审计与回滚   — 发现违规、撤销后果          （兜底，最后手段）
Layer 3  环境沙箱     — 物理上做不了                （强）
Layer 2  产物门       — 产物不过门就不生效           （强）
Layer 1  工具中介     — agent 只能用我们的工具       （最强）
Layer 0  规则声明     — prompt / instructions      （引导，非控制）
```

**要点**：

- **Layer 0 不是控制**，只是引导。真正的强制在 L1–L3。
- **越往下越强**：agent 跑在我们的环境、只能用我们的工具 → 强制近乎完备（物理上没别的路径）。
- **纵深**：任何一层被绕过，下一层兜住。

### 3.1 Layer 1 · 工具中介（最强）

**agent 只能通过注册的工具/方法行动。** 它想干的事，必须表达成对工具的调用；工具层是唯一的出口。

- 工具注册制：未注册的能力**无法调用**
- 工具前置检查：调用前校验参数、权限、规则
- 天然 agent 无关：不管谁调，都走同一层

### 3.2 Layer 2 · 产物门（强）

**agent 的产物在通过门之前是"惰性"的**——不生效。

| 产物 | 门 | 不过的后果 |
|---|---|---|
| 用例 | 确认门 | 不成立 |
| 场景/步骤 | 校验门 | 不入库 |
| 代码改动 | 提交门 | 提交不了 |
| 部署 | 发布门 | 发布不了 |

**agent 可以产出任何东西，它只是不生效。**

### 3.3 Layer 3 · 环境沙箱（强）

**物理上做不了。** 比"检查后拒绝"更强——根本不给路径。

- 文件系统：只能写指定目录
- 网络：只能连白名单
- 命令：只能跑白名单
- 凭据：不注入就不存在

### 3.4 Layer 4 · 审计与回滚（兜底）

前面都失效时的最后手段：**发现违规、撤销后果**。

- 全量审计（谁、何时、做了什么）
- 违规检测（规则偏离告警）
- 回滚能力（撤销已生效的坏后果）

## 4. 两类场景，两套关口

| 场景 | agent 是谁 | 关口 | 现有基础 |
|---|---|---|---|
| **A. agent 开发平台自身** | claude code / cursor / … 改仓库 | **提交/合并**（commit / PR） | `agent/file_write_approval.py`、`agent/code_run_approval.py`、`.git/hooks/post-commit` |
| **B. agent 通过平台干活** | 任意 agent 用能力面 | **能力面 + 产物入库** | 工具层、八道门禁 |

### 4.1 场景 A：开发时

- agent 在 worktree 里**随便改**（自由度高，不影响他人）
- 但**过不了门就 commit / merge 不了**：pre-commit 校验、CI 门禁、分支保护
- 越界写（撞 allowed_roots / denied_patterns）→ **一次性审批卡**（已实现）
- **关口 = 仓库**：本地随意，生效点设卡

### 4.2 场景 B：使用时

- agent 只能用**注册工具/方法**行动
- 产物（用例/场景/报告）**过不了门就不生效**
- 执行由**引擎**跑，agent 不能绕过断言
- **关口 = 能力面 + 入库**

## 5. 规则分类：不可机器检查的，不算规则

| 规则类型 | 可检查 | 强制 |
|---|---|---|
| 结构 / schema | ✅ | 硬拦 |
| 禁止操作 | ✅ | 拦 |
| 必需元素（"每步必须有断言"） | ✅ | 拦 |
| 语义约束 | ✅（配合分析） | 拦 / 警告 |
| 质量 / 风格 | 部分 | 警告 |
| "把活干好" | ❌ | **不可强制，不假装** |

**设计纪律**：**每条可强制的规则必须配一个检查器。** 没有检查器的规则是愿望，不是规则。

**规则要声明式 + 可版本化**：规则住在平台（不是 agent 的 prompt 里），可审计、可演进。

## 6. 逃生口（规则错了怎么办）

规则一定有错的时候。逃生口必须是：

| 要求 | 说明 |
|---|---|
| **人来豁免** | 不是 agent 自己豁免——这正是整套设计要防的 |
| **显式留痕** | 记录谁批的、为什么 |
| **有范围** | 一次性 / 限时 / 限定对象，不是永久 |
| **绝不** | "agent 决定跳过检查" |

**形式**：一次性审批卡（已有 `file_write_approval` 的范式）——超范围 → 卡住 → 人批 → 放行一次。

## 7. 反馈闭环（让 agent 能合规）

只会拦的强制很挫败。好的强制：

```
agent 产出 → 门校验 → 不过 → 返回结构化错误（哪条规则/在哪/怎么改）
                              → agent 修正 → 重试（限 N 次）
                              → 仍不过 → 升级给人
```

- **结构化错误**：`{path, rule, msg, severity, hint}`
- **可重试**：agent 拿反馈改，不直接判死
- **有上限**：N 次后交人，避免无限循环烧 token

## 8. 落到平台（落地映射）

| 层 | 平台落点 |
|---|---|
| L1 工具中介 | 工具层注册表 + 能力面（第十七节）；未注册即不可调 |
| L2 产物门 | 八道门禁（知识/确认/生成/校验/执行/保证/根因/变更） |
| L3 环境沙箱 | 执行沙箱（文件/网络/命令白名单）、凭据不注入 |
| L4 审计回滚 | `agent/tool_audit.py`（已有）+ 变更记录 + 回滚 |
| 规则 | 校验器（确定性代码）+ 声明式规则集 |
| 逃生口 | 一次性审批卡（`file_write_approval` 范式） |

## 9. 与"任意 agent"的兼容

因为强制挂在**关口**（不是 agent 侧），所以：

- 换 agent（pi / dsh / claude code / 自研）→ 关口不变
- agent 无 hook → 不影响（我们不用它的 hook）
- agent 忽略 prompt → 不影响（prompt 不是控制层）

**这就是"不管用哪个 agent 都要遵守"的答案：遵守不是因为 agent 配合，而是因为它不遵守就产不出有效果。**

## 10. 设计决策

| # | 问题 | 决策 | 理由 |
|---|---|---|---|
| 1 | 规则声明格式 | **声明式规则集（YAML）+ 检查器（Python 代码）**；简单规则纯声明，复杂规则挂代码 | 声明式可审计可版本化；代码兜住表达力 |
| 2 | CI 阻断清单 | **结构/schema、禁止操作、必需元素、引用可解析 → 阻断**；质量/风格 → 告警 | 硬规则阻断，软规则告警 |
| 3 | 沙箱白名单 | 见 06 §6.3 | 单一出处 |
| 4 | 审批授权粒度 | **按人授权**；有效期默认**一次性**（可升为限时） | 最小授权，防长期口子 |
| 5 | 违规升级策略 | **默认告警 → 累计触发阻断 → 严重上报** | 渐进，不误伤 |
