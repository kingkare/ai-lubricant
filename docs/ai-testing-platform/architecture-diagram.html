流程图 · 用例生成

从需求文档到用例进库。AI 产物先落暂存区，人确认了才进正式表——三道需要人拍板的停顿点用黄色标出。

环节 0需求入口人 + 可选 AI

五条入口：浏览器连着打开的文档（飞书 / Confluence）、本地文档、URL、文件上传、手工录入。原始内容先存下来，再建需求记录。

落原始层 → 建需求
环节 1需求分析AI 思考

每条需求一个会话、并行：看缺什么、有没有说不清、能不能写成条件和预期，产出结构化分析和一份问题清单。写得太含糊的过不了四条标准，停在「分析未过」。

四条标准不合格不放行
门⓪需求评审人拍板

AI 先评需求文档本身好不好，逐条给证据和建议；然后一次只问一个问题、每个问题带推荐答案，最多问 10-15 个。问到没预算了就自动按推荐答案往下走，人可以再改回来。人确认需求过关才继续。

需求过关
环节 3测试点提取 + 分派AI 分工

先按影响和概率给方向定权重，再每个方向派一个 AI 并行提测试点；接口方向机械铺一遍，另一个供应商的模型查漏。每个测试点带上：五个字段、覆盖轴、设计方法、批次、依据（事实 / 推断 / 待确认三色）。

定每个点测哪些端
环节 4覆盖补全主要是代码

铺一张「覆盖轴 × 端」的表，查漏查重：空格子补测试点，不适用的必须写清依据。

热力图亮 / 灰 / 斜纹
门①需求确认人拍板

人看着测试点和覆盖图：答问题、点改端归属、勾选「确认入选」或「打回」。这个需求下的点全确认了，才进用例生成——不等别的需求。

确认过的测试点
环节 5用例细化AI 写

按「测试点 × 端」派活（只给路径不给正文）：六种设计策略显式过一遍 → 先写行为 → 再单独设计断言 → 每个功能点 1 条正向 + 至少 3 条异常/边界 → 数据按五个作用域归位 → 查重。产物只写进暂存区。

先进暂存区，不碰正式表
环节 6评审代码 + 两个 AI 互评

三道闸：① 代码查硬伤（证据够不够、有没有编造的接口/选择器、断言是不是只有 200、硬编码、配比、规则回执）；② 两个不同供应商的 AI 各看一半、互不见面，必须意见一致；③ 五维打分，不及格打回重写，重写版本不许比上一版断言更少。

分歧不自动裁决，带两份意见交给人
门②用例确认人拍板

按「测试点 × 端」分组看：组头显示五维分和双评意见，四种判断——保留 / 就地改 / 打回（必须选原因）/ 先挂起（关联一个问题）。确认了才进正式表；有问题打回的，之后修好了可以重开一轮只重跑它。

进正式表
环节 7场景化

用例说的是「测什么」，场景是「怎么跑」。接口的参数/格式类直接机械翻译成步骤；字段规则、接口逻辑、网页和 App 的场景必须真跑一遍探索，用真实轨迹替换推测的步骤，然后把改动包拿给人签。

回流越用越准

打回原因、缺陷结案、返工教训都存进问题库；评审通过且分高的用例打上黄金标记，下一轮同模块生成时优先拿来当范例。

流程图 · 执行到报告

从场景化好的用例跑到最终报告。失败先分类，不是所有失败都算数。

环节 8执行确定性引擎

跑之前 SQL 语句先过红线闸（没有 WHERE 的更新删除、查敏感字段、大表没加 LIMIT → 直接拒绝）。按冒烟/重点/扩展分波次跑，抖动的先隔离掉，互不相关的才并行。

每条结果归到四种状态之一
过通过

接着往下走。

挂判定是产品缺陷

进缺陷环节。

判不了环境抖动 / 脚本问题

不算失败率、不产 bug：环境的回隔离区重测，脚本的回场景化重写。

没裁用例过期 / 被跳过

用例过期的回门②打回重做；跳过的不算失败率的分母。

「挂」的进缺陷
环节 9缺陷代码分流 + AI 分析

建单前先查是不是同一个原因（像就提示合并）→ 规范化六段单，复现步骤从用例继承 → AI 定级和人工改级的一致率记账 → 八步分析（现象、影响模块、翻日志、推荐 SQL、关联历史缺陷、回归范围、风险、复核点；没日志不许下根因结论）→ 沿 trace 定位到代码行 → 修复验证七点。

修完验证
环节 10回归 + 上线判定 + 报告

按这次改了哪些代码算出必须测 / 建议测 / 抽测三级清单 → 跑回归。上线要看两个条件同时满足才放行（共识是「上」且置信度达到 0.9），不够就拦下并给出理由；回滚触发条件提前声明好。报告结论必须有执行数据支撑，分四种受众展示。

回流下一轮更准

优质脚本进范例库、缺陷模式进模式库、覆盖事实更新测试画像，回流到需求环节。

三道停顿点

停在哪什么时候人干什么
门⓪ 需求评审分析完、提测试点之前看 AI 给的需求质量报告，确认需求过关
门① 需求确认测试点和覆盖图出来后答问题、改端归属、勾选确认入选
门② 用例确认用例评审打分完保留 / 就地改 / 打回 / 先挂起
