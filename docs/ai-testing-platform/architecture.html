AI 测试平台

把平台从开发工具升级为生产平台——测试是与开发平级的角色，拥有自己完整的知识、资产、能力与流程，而不是给开发流程加一个附属环节。

三条不可动摇的原则：AI 不裁判，框架裁判 · 确定性的归确定性 · 对 AI 固定，对人可扩展。

定位：本服务内的一个能力域，与 GA（GenericAgent）无关、不借用其概念。只讲框架、理念、体系与底层设计；表结构为关键字段摘要（非最终 DDL）。

本页目录 一、定位 二、设计理念 三、总体架构 四、知识体系 五、资产体系 六、能力体系 七、流程体系 八、质量体系（门禁） 九、底层数据设计 十、能力面契约 十一、Agent 强制（四层防御） 十二、落地状态 十三、关键决策

一、定位

开发只是其中一个角色。本设计要补的是测试者——一个与开发者平级、拥有独立世界观的角色。

测试是平级角色

不是"给开发流程加一个环节"，而是增加一个独立角色：有自己的知识视角、产出物、判断标准。

它有自己的世界观

测试视角的知识（要测什么、测过什么、坏过哪里、覆盖如何），以及自己的产出（用例、场景、缺陷、根因）。

它有自己的判断标准

门禁与准则——产物不达标不放行，且判定由框架（机器）完成，不由 AI 完成。

二、设计理念

八条理念，是整个体系的地基。其中 #2「AI 不裁判，框架裁判」 是最根本的一条——没有它，AI 的产出无法被信任。

#理念说明
1知识是公共资产抽取出来的知识服务于整个平台——开发能用、测试能用。测试只是在它之上多了一层测试视角。
2AI 不裁判，框架裁判AI 负责"想"和"写"，但是否合格由框架判定。这是整个设计的根。
3确定性的归确定性执行脚本、跑断言、校验规范是确定性的，不需要 AI；分析、归纳、设计、生成、诊断才需要 AI。两者严格分开。
4对 AI 固定，对人可扩展AI 只能在已注册的能力范围内组合；人要加新能力，走评审流程。这是可控性的来源。
5一切皆可沉淀每完成一次工作，经验（优质脚本、缺陷模式、规范约定）都回流成资产，让下一次更准。
6分层解耦，变更局部化知识、用例、场景、工具各自独立分层。改一处不动全身。
7变更必有因，产出必有责用例和场景的任何变更都要记录理由；用例的变更必须显式传导到关联场景。设计者对设计的用例负责到底。
8疑问不靠猜分析设计中必然产生疑问。疑问作为一等公民进入流程，通过调试/文档/用户确认闭合，不能靠 AI 假设填平。

三、总体架构

三层结构：底层是平台对"系统真相"的公共认识，中间是测试视角的投影，最上层是执行测试的角色。

┌──────────────────────────────────────────────────────┐ │ AI 测试者（角色） │ │ 规划 → 分析 → 设计 → 编码 → 执行 → 调试 → 报告 │ ├──────────────────────────────────────────────────────┤ │ 测试知识引擎 │ │ 需求 · 规则 · 用例 · 缺陷 · 文档 · 代码 · 接口 │ │ 历史 · 证据 · 覆盖 · 结果 │ ├──────────────────────────────────────────────────────┤ │ 软件知识图谱 │ │ 代码图谱 + 知识化 + 业务规则 │ │ ├── 代码 ├── 文档 ├── 业务规则 │ └──────────────────────────────────────────────────────┘
层是什么作用
软件知识图谱最底层，是平台对"系统真相"的认识：代码是什么、文档说什么、业务规则怎么定义公共底座，开发/测试共用
测试知识引擎在底座之上，组织出测试视角的知识：要测什么、测过什么、坏过哪里、覆盖如何测试域专用（派生视图）
AI 测试者最上层，是执行测试的角色从知识引擎取知识、向它写产出
关键边界测试视图只读底座，不回写底座——回写走正规摄取。底座是公共资产，测试域在其上派生，二者物理分离。

四、知识体系

知识来自三个源，独立抽取、独立成资产。知识 ≠ 用例：知识是对世界的结构化认识，用例是一个流程说明；写用例参考知识，但知识的存在不为了用例。

知识源 │ ┌──────────────────┼──────────────────┐ ▼ ▼ ▼ 产品知识 技术知识 测试知识 ──────── ──────── ──────── PRD CodeGraph 人工用例 产品文档 API AI 用例 接口文档 DB 历史 Bug 业务规则 MQ 测试报告 ADR Config 测试结果 Wiki Dependency 缺陷根因
源回答什么性质
产品知识应该做什么业务侧定义
技术知识实际是什么技术侧实现
测试知识测过什么、坏在哪测试侧产出（既是输入也是产出）

四层存储（从原始到可用）

L1 原始层 Raw 不可变的原文快照 + 溯源 ↓ 解析/抽取 L2 结构化层 Item 结构化知识条目（规则/接口/组件/表…） ↓ 关联 L3 图谱层 Graph 条目 ↔ 锚点 ↔ 条目的关系 ↓ 派生 L4 视图层 View 面向消费者的投影（画像/覆盖/影响面）
L4 不手工维护——它是查询结果，不是数据。这是"数据只有一份真相"的保证。

锚点：精确对齐，不用向量

锚点是对齐层——让产品知识、技术知识、测试知识能在同一坐标上对上。身份为 (project_id, kind, path, symbol)，稳定、可 grep、不随行号漂移。

锚点 kind来源
endpoint路由定义
function / class符号表
route前端路由配置
table迁移文件 / schema 文件
config_key配置文件
工具即抽取器不重造轮子——跑现成工具（CodeGraph 出代码符号/调用边、Graphify 出文档↔代码引用边、codetospec 出业务规则+drift），平台只做 adapter + 入库 + 统一查询 + 门禁。用我们自己的稳定身份入库，不照搬工具的 ID（行号漂移即断）。

三档置信度

declared（显式声明）> extracted（确定性解析 1.0）> inferred（LLM 猜测 0.55–0.95）。诚实标注"这是解析出来的还是猜的"。

歧义即丢弃

一个歧义的名字是猜测，猜测不是边。召回换精确，与门禁哲学一致。

注释是一等公民

docstring / # WHY: / ADR 引用抽成节点，rationale_for 边把"为什么这么写"接进图——文档↔代码关联最便宜可靠的入口。

五、资产体系

测试者产出的东西，四类资产，各自独立。核心不变式：AI 只能组合已注册的工具/方法写场景；要新能力必须走评审流程。

标签 ──划分用途（任务按标签选，不直接选用例） │ 用例 = 数据 + 场景引用 + 标签 ← 业务视角（测什么） │ ↕ 多对多 场景 = 步骤集合 + 局部变量 ← 实现视角（怎么测） │ 步骤 = 类型 + 描述 + 参数/方法 + 后置校验 ← 类型化 │ 方法脚本 = 基础脚本库 + 项目脚本库 ← Python 代码住这里

5.1 用例（业务视角）

用例只说"要测什么、预期是什么"，不含实现细节（不含步骤）。

为什么不把步骤写进用例用例若解释"每一步干啥"，会写得很详细，用例的重点反而抓不住。步骤属于场景。

用例的创建准则（必须确认，不能凭空）：

来源确认方式
调试通过实际运行/复现确认
文档通过 PRD / 接口文档 / 业务规则确认
用户确认产品不确定时，由用户拍板

产品不确定 → 必须走用户确认。发现产品定义不清、行为有歧义时，用例不得自行假设，必须挂起为"待确认"，交用户裁决后才成立。

5.2 场景（实现视角）

场景 = 步骤集合 + 局部变量管理。它的作用是实现用例，一个场景可被多个用例关联。步骤类型化：

type用途
request发送请求
page / android / ios操作页面 / 移动端
wait等待
script执行方法脚本或内联代码
check校验数据
sql / ws / custom数据库 / WebSocket / 自定义工具
ai_judge / agent_action / agent_workflowAI 判断 / Agent 操作 / Agent 工作流（执行语义下沉到步骤类型）
局部变量流转场景内声明 local_vars，步骤 post_cond 写入、后续步骤读取；前置场景的变量传递给当前场景——这就是上下场景互相使用的机制。

5.2c 脚本创建准则（机器强制）

准则含义
设计提取，不要从头到尾场景必须尽可能拆分，可复用部分提取为方法/自定义工具
复用优先同逻辑二次出现必须提为方法/工具
校验必需每个步骤至少一条后置校验
环境变量环境相关的值必须走环境变量，不硬编码
依赖白名单只能用注册工具/方法
清理对称 · 幂等可重跑前后置对称、资源必释放、重复执行不污染
溯源完整场景 → 用例 → 需求 链完整

5.3 缺陷与根因

失败 → 分类 → 提缺陷 → 根因分析 → 修复 → 回流。根因分析的产出必须带证据链——每条结论可溯源到代码位置、日志、证据，无证据的结论不入库。

5.4 沉淀（测试技术）

让不同 AI 产出一致的关键——四件套：

1约定

命名 / 目录 / 变量 / 错误处理规范。

2模板

骨架，AI 填空。

3黄金样例

已验收的优质脚本，作参照。

4校验器

机器判定"是否符合规范"。

一致性 = 约定(读) + 模板(填) + 样例(仿) + 校验器(判)。沉淀分三层：通用（跨框架）→ 框架级 → 项目级，AI 按当前上下文按需加载。

六、能力体系

6.1 AI 测试者的七个角色

规划→ 分析→ 设计→ 编码→ 执行→ 调试→ 报告
角色职责性质
规划制定整体测试策略智能
分析归纳知识、找缺口智能
设计设计测试方案智能
编码生成用例与场景智能
执行跑脚本、判结果确定性
调试分析失败、定位根因智能
报告汇总质量视图、沉淀知识智能
这七个是角色，不是固定的程序——谁来完成是部署选择。执行这类确定性工作流根本不需要 agent，由脚本引擎直接跑。

6.2 Agent 抽象（本阶段不选路）

平台不绑定任何具体 agent。测试域对外只暴露四个面——"接 pi 还是 dsh 还是别的"是部署选择，不是架构改动：

工具方法

原子可调用单元（最底层）。

MCP

工具方法的 MCP 暴露，任何会说 MCP 的 agent 都能调。

接口

契约：输入输出、能力保证、域边界。

AI 工作流

七个角色的编排定义。

6.3 任务（每次启动的用途不一样）

不同测试场景下没必要整个用例集跑一遍，应该有侧重点。任务 = 一次有侧重、有标签、有通知的启动。

任务包含说明
场景标签按标签选例（不是直接选用例）——跑的时候按标签划分用途
执行类型多维度启动：手动 / 定时 / 事件 / 接口
通知配置执行结果需要通知（通道 + 时机 + 内容）
任务用途描述 / 标题这次跑是为了什么
全局参数本次任务所有场景共享的参数
标签有分类（用途 / 优先级 / 模块 / 测试类型），任务可按不同维度组合选例，如"模块=支付 且 优先级=P0"。任务提供接口，人和 AI 都能添加/修改。

七、流程体系

完整流水线，14 段，循环——最后一段的产出回流第一段，系统越用越准。

多源知识 → 分析归纳 → 知识模型 → 测试设计 → 用例 → 脚本生成 → 脚本验证 → 执行测试 → 结果分析 → 缺陷分析 → 缺陷提交 → 根因分析 → 测试报告 → 质量沉淀 ↺
段承担角色
多源知识 / 分析归纳 / 知识模型分析
测试设计 / 用例设计
脚本生成 / 脚本验证编码
执行测试 / 结果分析执行（确定性）
缺陷分析 / 缺陷提交 / 根因分析调试
测试报告 / 质量沉淀报告

规划贯穿全程：先定策略，再动态编排其余角色。关键：这是循环，不是直线。优质脚本进沉淀，缺陷模式进知识，覆盖事实更新画像。

7.1 疑问与确认（流程的一等公民）

分析与设计过程中一定会产生疑问，这些疑问不能消失，必须显式表达并收敛。两类来源：产品侧不确定（PRD 没写清、行为有歧义）、设计侧疑问（接口契约与文档不一致）。

疑问提出 │ ├── 调试验证（跑一下就知道）─────────┐ ├── 文档/代码确认（查得到答案）──────┤ └── 用户确认（产品不确定时必须走）────┤ ▼ 结论回写知识 / 用例

7.1.1 疑问分诊（提交用户后的第一步是"归类"）

上一步"用户确认"不是终点，是起点。提交给用户的疑问，第一件事是判断它属于哪一类——类型决定后续走哪条路。

类型含义后续
bug已有定义被违反 / 系统缺陷 / 理解错了走修 bug 流
需求问题产品未定义、行为有歧义、要拍板走产品决策
设计问题设计不自洽、约束冲突走设计修订
问错 / 信息不足问题本身有问题、超范围补上下文后重问
两条硬规则① 不许 AI 自行假设填平（无论多小的疑问）——自己拍 = 越权。② 不许把未分析的疑问直接扔回用户——先分析合理性 + 给出归类建议，再交用户裁决。
疑问阻塞下游用例带着 open 疑问，不得进入脚本生成；脚本带着 open 疑问，不得进入执行。每个疑问有状态：open → 已解决，附解决方式与依据。

八、质量体系（门禁）

整个设计的信任基础：AI 不裁判，框架裁判。每个环节都有门，产物不达标不放行。

门判什么
知识门结构化 + 可溯源 + 可测
生成门契约合法 + 只用已注册工具 + 可断言 + 可溯源
校验门脚本写没写校验——每步、每个关键结果都有可判定校验
确认门用例依据是否可确认（调试/文档/用户确认）；未解决的疑问是否已收敛
执行门断言由框架机械判定
保证门可执行 + 可稳定通过 + 有增量价值
根因门每条结论带证据引用
变更门每次变更是否记录理由；用例变更是否已传导到关联场景
门禁是机器，不是 AI——这是"不同 AI 产出一致"的机制保证。

8.1 失败分流（与疑问分诊同构：先归类，再决定走哪条路）

结果判据处理
script_issue定位/时序/断言写法问题自愈或转人工
product_bug断言合理但系统行为不符建测试缺陷（mc_test_bug）
case_outdated需求已变，预期过时标用例 deprecated
env_flaky重跑即过标 flaky，不计失败

判据顺序（确定性优先）：重跑一次 → 比对知识库预期 → 判失败层（脚本层 vs 系统层）→ 不确定才交 AI。失败指纹相同则归并到同一缺陷。

8.2 三模执行（per case 可选，工业级容错）

模式流程
script_only引擎跑 → 判定（默认，纯确定性）
hybrid引擎跑 → 失败 → Debugger 诊断 → 自愈建议 → 修场景 → 重跑
ai_only无场景，AI 直接执行（仍只用注册工具/方法，断言仍机械判）
hybrid 自愈边界只改场景/步骤（不改被测代码）；有次数/时间/token 预算；改完重新过校验门；重跑后仍由断言库判定（AI 不能自判 pass/fail）。

九、底层数据设计

三条治理铁律贯穿全部实体：稳定 ID、显式状态机、版本 + 溯源。测试域表统一 mc_test_* 段，知识为平台公共资产用 mc_knowledge_*，沿用服务存储惯例（Postgres + Tortoise ORM + UUID 主键）。

9.4 出入准则与变更传导

进

过保证门才入库，不达标降级为"候选"。

改

只增版本，不覆盖历史；每次变更必须记录理由。

废

标失效，不物理删除，通知依赖方。

删

仅限误建，人工确认。

十一、Agent 规则强制（四层防御）

核心原则Agent 是随机的，你无法保证它"想"什么。任何试图"让 agent 遵守"的做法（写进 CLAUDE.md、prompt 叮嘱）本质是建议，agent 可忽略——不是强制。强制的本质：agent 的所有动作，必须经过我们控制的关口才能生效。不合规的动作不生效——不是"告诉它别做"，而是"做了也没用"。
Layer 4 审计与回滚 — 发现违规、撤销后果 （兜底，最后手段） Layer 3 环境沙箱 — 物理上做不了 （强） Layer 2 产物门 — 产物不过门就不生效 （强） Layer 1 工具中介 — agent 只能用我们的工具 （最强） Layer 0 规则声明 — prompt / instructions （引导，非控制）
层机制要点
L1 工具中介agent 只能通过注册的工具/方法行动，工具层是唯一出口未注册的能力无法调用；调用前校验参数/权限/规则；天然 agent 无关
L2 产物门产物过门之前是"惰性"的——不生效用例不过确认门不成立；场景不过校验门不入库；代码不过提交门提交不了
L3 环境沙箱物理上做不了，比"检查后拒绝"更强文件系统限目录、网络限白名单、命令限白名单、凭据不注入就不存在
L4 审计与回滚前面都失效时的最后手段全量审计、违规检测、回滚能力（撤销已生效的坏后果）
设计纪律每条可强制的规则必须配一个检查器。没有检查器的规则是愿望，不是规则。"把活干好"这类不可机器检查的——不假装能强制。
